# LearnPython — Backend

This is the server-side component of LearnPython. It is a Django 5.2 application with a single `api` app that exposes a RESTful JSON API used exclusively by the React frontend. There is no authentication, no user model, and no session management — every endpoint is public.

```python
DEBUG = os.getenv("DEBUG", "false").lower() in ("true", "1", "yes")
```

Defaults to `*` which works for both local dev and Render (Render sets its own host). Tighten this in production if needed.

## 4. Data Models

Defined in `api/models.py`. There are three models with a simple one-to-many chain: `Course → Lesson → Exercise`.

### Course

```python
class Course(models.Model):
    title       = models.CharField(max_length=200)
    description = models.TextField()
    order       = models.IntegerField(default=0)
    icon        = models.CharField(max_length=50, default="📘")  # emoji
```
`Meta.ordering = ["order"]` — courses are always returned in order without needing to specify it at query time.

### Lesson

```python
class Lesson(models.Model):
    course         = models.ForeignKey(Course, on_delete=models.CASCADE, related_name="lessons")
    title          = models.CharField(max_length=200)
    subtitle       = models.CharField(max_length=300, blank=True)
    content_blocks = models.JSONField(default=list)
    order          = models.IntegerField(default=0)
```

`content_blocks` is a JSON array of block objects. Each block has at minimum a `type` field and a `body` field. The frontend's `ContentBlock` component switches on `type` to decide styling:

| type | rendered as |
|---|---|
| `"text"` | `ReactMarkdown` — supports full GFM Markdown |
| `"code"` | `<pre>` block with PrismJS Python highlighting |
| `"tip"` | Styled callout box (blue) |
| `"warning"` | Styled callout box (amber) |

Example content block:
```json
{
  "type": "text",
  "body": "## Variables\n\nA variable stores a value. Use `=` to assign:\n\n```python\nname = \"Alice\"\nage = 25\n```"
}
```

### Exercise

```python
class Exercise(models.Model):
    lesson       = models.ForeignKey(Lesson, on_delete=models.CASCADE, related_name="exercises")
    title        = models.CharField(max_length=200)
    instructions = models.TextField()
    starter_code = models.TextField(blank=True)
    hint         = models.TextField(blank=True)
    solution     = models.TextField(blank=True)
    explanation  = models.TextField(blank=True)
    tests        = models.JSONField(default=list)
    order        = models.IntegerField(default=0)
    difficulty   = models.CharField(choices=[("easy","Easy"),("medium","Medium"),("challenge","Challenge")])
```

The `tests` field is a JSON array used by the sandbox's `run_exercise_tests()` function:

```json
[
  {"input": "",      "expected_output": "Hello, World!"},
  {"input": "Alice", "expected_output": "Hello, Alice!"}
]
```

When `input` is `""`, the regular execution path is used. When non-empty, it is injected as `sys.stdin` via `io.StringIO`.

The `solution` and `explanation` fields are never included in the standard `ExerciseOutSerializer` — they are only returned via the dedicated `/api/exercises/:id/solution` endpoint.

## 5. Serializers

Defined in `api/serializers.py`. DRF serializers handle two things: (1) validating input and (2) controlling the exact JSON shape of output.

### CourseOutSerializer

```python
class CourseOutSerializer(serializers.ModelSerializer):
    lesson_count = serializers.IntegerField(read_only=True)
    class Meta:
        model = Course
        fields = ["id", "title", "description", "order", "icon", "lesson_count"]
```

`lesson_count` is not a model field — it's injected via a `annotate(lesson_count=Count("lessons"))` in `list_courses()`.

### LessonDetailSerializer

Nested serializer that embeds all exercises on a lesson:

```python
class LessonDetailSerializer(serializers.ModelSerializer):
    exercises = ExerciseOutSerializer(many=True, read_only=True)
    class Meta:
        model = Lesson
        fields = ["id", "course_id", "title", "subtitle", "content_blocks", "order", "exercises"]
```

`exercises` is populated from the `related_name="exercises"` FK relationship and DRF's `prefetch_related` is triggered by calling `.get(pk=lesson_id)` with `prefetch_related("exercises")` in the view.

### ExerciseOutSerializer

Intentionally excludes `solution`, `explanation`, and `tests` to prevent leaking answers:

```python
fields = ["id", "lesson_id", "title", "instructions", "starter_code", "hint", "difficulty", "order"]
```

### App (`api/urls.py`)

```

GET  api/lessons/<int:lesson_id>              → get_lesson
```

## 7. Views

All views are function-based and decorated with `@api_view(...)` and `@permission_classes([AllowAny])`. Defined in `api/views.py`.

### list_courses

```python
courses = Course.objects.annotate(lesson_count=Count("lessons")).all()
```
Uses `annotate` to add a SQL `COUNT` subquery so `CourseOutSerializer` can include `lesson_count` without N+1 queries.

### list_lessons

Returns a manually-constructed list of dicts (not a serializer) because it adds two synthetic fields:
- `is_completed` — always `False` (server-side; completion is stored in localStorage on the frontend)
- `is_locked` — always `False` (all lessons are unlocked; the original design had locking but it was removed)

### get_lesson

```python
lesson = Lesson.objects.prefetch_related("exercises").get(pk=lesson_id)
```
`prefetch_related` does a second SQL query to fetch all exercises at once, then Python-side joins them — avoiding N+1 when the nested serializer iterates exercises.

### run_code

1. Validates code is present and within `_MAX_CODE_LENGTH`.
2. Calls `_run_async(execute_code(code))` — wraps the asyncio coroutine in `asyncio.run()`.
3. Passes the raw error to `explain_error()` to generate a friendly message.
4. Returns `{output, error, friendly_error, execution_time_ms}`.

### submit_exercise

Same flow as `run_code` but calls `run_exercise_tests(code, exercise.tests)` and additionally returns `{is_correct, test_results[], message}`.

### _run_async helper

```python
def _run_async(coro):
    return asyncio.run(coro)
```

Django views are synchronous. `execute_code` and `run_exercise_tests` are defined as `async def` (they use `asyncio.wait_for` internally). `asyncio.run()` starts a new event loop, runs the coroutine to completion, and returns the result — this is thread-safe as long as each request gets its own event loop call.

## 8. Sandbox: Code Execution Engine

`sandbox.py` is the most security-critical file in the project. It runs untrusted Python code from students in an isolated subprocess.

### Execution pipeline (in order)

#### Step 1: Django request body size limit

Before any view code runs, Django's `DATA_UPLOAD_MAX_MEMORY_SIZE` (default: 256 KB) causes Django to reject request bodies that are too large with a `RequestDataTooBig` exception.

#### Step 2: View-level code length check

```python
if len(code) > _MAX_CODE_LENGTH:  # default 10,000 characters
    return Response({"detail": "Code is too long."}, status=400)
```

Runs before calling into the sandbox at all.

#### Step 3: check_code_safety(code)

Two independent checks:

**a) Character and line count:**
```python
if len(code) > settings.SANDBOX_MAX_CODE_LENGTH:
    return False, "Your code is too long..."
if len(code.splitlines()) > 500:
    return False, "Your code has too many lines..."
```

**b) Blocked pattern scan:**
The code (and a whitespace-normalised copy) is checked against ~45 blocked strings. These include:
- Dangerous stdlib imports: `import os`, `import sys`, `import subprocess`, `import socket`, `import http`, `import urllib`, `import pathlib`, `import pickle`, `import ctypes`, `import importlib`, `import threading`, `import multiprocessing`, `import concurrent`, `import signal`, `import resource`
- Meta-programming builtins: `eval(`, `exec(`, `compile(`, `__import__(`, `globals(`, `locals(`, `getattr(`, `setattr(`, `delattr(`
- Object internals: `__builtins__`, `__subclasses__`, `__class__`, `__bases__`, `__mro__`, `object.__`
- File/process: `open(`, `exit(`, `quit(`, `breakpoint(`
- Memory-allocation patterns: `bytearray(`, `memoryview(`

**c) Import whitelist:**
Any `import X` or `from X import ...` line where `X` is not in the allowed list is rejected. Allowed list: `math`, `random`, `string`, `datetime`, `collections`, `itertools`, `functools`, `json`, `re`, `statistics`, `decimal`, `fractions`, `textwrap`.

The whitelist check handles both `import mod1, mod2` (multi-import) and `from module import name` syntax. It strips inline comments before parsing.

#### Step 4: Wrapper template injection

The student's code is indented by 4 spaces and substituted into `WRAPPER_TEMPLATE`:

```python
WRAPPER_TEMPLATE = '''
import sys
import io

sys.setrecursionlimit(200)

# OS-level resource limits (Linux/Render only — silently skipped on Windows)
try:
    import resource as _resource
    _MEM = {max_memory}
    _resource.setrlimit(_resource.RLIMIT_AS, (_MEM, _MEM))   # virtual memory cap
    _resource.setrlimit(_resource.RLIMIT_CPU, ({timeout}, {timeout}))  # CPU time cap
except Exception:
    pass

_captured_output = io.StringIO()
sys.stdout = _captured_output
sys.stderr = _captured_output

try:
    {student_code}
except MemoryError:
    print("MemoryError: Your code used too much memory and was stopped.")
except Exception as _e:
    print(f"{type(_e).__name__}: {_e}")

sys.stdout = sys.__stdout__
sys.stderr = sys.__stderr__
_result = _captured_output.getvalue()
if len(_result) > {max_output}:
    _result = _result[:{max_output}] + "... (output truncated)"
print(_result, end="")
'''
```

The wrapper:
- Sets `sys.setrecursionlimit(200)` — prevents deep recursion from crashing the interpreter
- Uses `resource.setrlimit` to cap virtual address space (memory) and CPU time at the OS level. On Linux (Render), this hard-kills the process if it exceeds the limit. On Windows (local dev), the `try/except` silently skips it
- Redirects stdout/stderr to an `io.StringIO` buffer — captures all print output including exceptions
- Truncates output to `SANDBOX_MAX_OUTPUT_CHARS`

For exercises that require simulated stdin (i.e., when `input()` is used), `WRAPPER_TEMPLATE_STDIN` is used instead. It additionally injects:
```python
sys.stdin = io.StringIO({stdin_data})
```
before executing the student code.

#### Step 5: Subprocess execution

```python
with tempfile.NamedTemporaryFile(mode="w", suffix=".py", delete=False, encoding="utf-8") as f:
    f.write(wrapped_code)
    tmp_path = f.name

result = await asyncio.wait_for(
    asyncio.to_thread(_run_subprocess, tmp_path),
    timeout=settings.SANDBOX_TIMEOUT_SECONDS,
)
```

`asyncio.to_thread` runs `_run_subprocess` in a thread pool worker so it doesn't block the Django event loop.

```python
def _run_subprocess(file_path):
    result = subprocess.run(
        [sys.executable, "-u", file_path],
        capture_output=True,
        text=True,
        timeout=settings.SANDBOX_TIMEOUT_SECONDS + 1,
        env={
            "PATH": os.environ.get("PATH", ""),
            "PYTHONPATH": "",
            "PYTHONDONTWRITEBYTECODE": "1",
        },
    )
```

The subprocess:
- Uses the same Python interpreter as the server (`sys.executable`) — no separate virtualenv needed
- Runs with a clean, restricted environment — no access to Django's env vars (SECRET_KEY, DATABASE_URL, etc.)
- Has its own `subprocess.run(timeout=...)` as a backstop
- The temp file is always deleted in the `finally` block

#### Step 6: Asyncio timeout

`asyncio.wait_for(..., timeout=SANDBOX_TIMEOUT_SECONDS)` wraps the entire thread. If the thread exceeds the timeout, a `TimeoutError` is raised immediately and a user-friendly message is returned. The thread itself continues running until the OS kills the subprocess via `subprocess.run(timeout=...)`.

### Sandbox limits summary

| Limit | Default | Mechanism |
|---|---|---|
| Request payload | 256 KB | `DATA_UPLOAD_MAX_MEMORY_SIZE` (Django) |
| Code length | 10,000 chars | View check + `check_code_safety` |
| Line count | 500 lines | `check_code_safety` |
| Recursion depth | 200 frames | `sys.setrecursionlimit()` in wrapper |
| Memory | 64 MB | `resource.RLIMIT_AS` (Linux only) |
| CPU time | 5 seconds | `resource.RLIMIT_CPU` (Linux only) |
| Wall-clock time | 5 seconds | `asyncio.wait_for` timeout |
| Subprocess backstop | 6 seconds | `subprocess.run(timeout=6)` |
| Output | 5,000 chars | Truncation in wrapper |

## 9. Error Explainer

`error_explainer.py` exports a single function `explain_error(raw_error: str) -> str`.

It maintains a list of `(regex_pattern, friendly_template)` tuples. On each call, it tries each pattern against the raw error string (captured from the subprocess's stderr). The first match returns the corresponding template, with regex capture groups substituted in.

The patterns cover the most common beginner errors:
- `SyntaxError: invalid syntax`
- `SyntaxError: EOL while scanning string literal`
- `IndentationError: expected an indented block`
- `IndentationError: unexpected indent`
- `NameError: name 'X' is not defined`
- `TypeError: unsupported operand type(s) for ...`
- `TypeError: X() takes ... positional arguments`
- `ValueError: invalid literal for int() with base 10`
- `ZeroDivisionError`
- `IndexError: list index out of range`
- `KeyError`
- `AttributeError`
- `RecursionError`
- `MemoryError`
- Timeout messages (produced by the sandbox itself)

Every explanation includes:
- The error type in bold
- Plain-English description of what went wrong
- The likely cause
- A concrete fix suggestion
- A minimal before/after code example where appropriate

If no pattern matches, a generic fallback is returned.

## 11. Management Commands (Seeding)

```bash
python manage.py seed
```

This custom management command (`api/management/commands/seed.py`) is the single source of truth for all curriculum content.

### What it does

1. Deletes all existing `Exercise`, `Lesson`, and `Course` rows (in that order, respecting FK constraints).
2. Creates 1 `Course`: "Python Basics".
3. Creates 10 `Lesson` objects with 2–3 `Exercise` objects each.

Each lesson is created with a `content_blocks` JSON array built inline in the Python script. This makes the content easily readable and editable directly in code without needing an admin UI.

### Lesson structure (simplified)

```python
L1 = Lesson.objects.create(
    course=course,
    title="What is Programming?",
    subtitle="...",
    order=1,
    content_blocks=[
        {"type": "text",    "body": "## Welcome!...(markdown)"},
        {"type": "code",    "body": "print('Hello, World!')"},
        {"type": "tip",     "body": "..."},
        {"type": "warning", "body": "..."},
    ],
)

Exercise.objects.create(
    lesson=L1,
    title="Your First Print",
    instructions="Write a print() statement that outputs: Hello, World!",
    starter_code="# Write your code here\n",
    hint="Use print() with the text in quotes.",
    solution='print("Hello, World!")',
    explanation="print() displays text to the screen. Text must be in quotes.",
    tests=[{"input": "", "expected_output": "Hello, World!"}],
    order=1,
    difficulty="easy",
)
```

The seed command is idempotent — running it multiple times always results in the same clean state. It prints a confirmation line per item created and a summary at the end.

## 12. Static Files (WhiteNoise)

WhiteNoise is configured to serve static files directly from Gunicorn, without needing nginx or a CDN:

```python
STATIC_ROOT = BASE_DIR / "staticfiles"
STATICFILES_STORAGE = "whitenoise.storage.CompressedManifestStaticFilesStorage"
```

During the build step on Render (`python manage.py collectstatic --noinput`), Django copies all static files from installed apps (including DRF's browsable API CSS/JS) into `staticfiles/`. WhiteNoise serves them with `Cache-Control: max-age=31536000, immutable` headers because `CompressedManifestStaticFilesStorage` appends a content hash to filenames.

The `staticfiles/` directory is committed to the repository. This is intentional — Render's ephemeral filesystem means the build must produce the full output, and having the staticfiles checked in ensures they are always available.

## 14. Custom Exception Handler

`api/utils.py` provides a custom DRF exception handler registered in `REST_FRAMEWORK["EXCEPTION_HANDLER"]`.

DRF's default handler returns errors in varying shapes — `{"detail": "..."}`, `{"field": ["error"]}`, `["error", "error"]`, etc. This custom handler normalises all of them into `{"detail": "<string>"}`:

```python
def custom_exception_handler(exc, context):
    response = exception_handler(exc, context)
    if response is not None:
        if isinstance(response.data, dict):
            if "detail" not in response.data:
                messages = []
                for field, errors in response.data.items():
                    if isinstance(errors, list):
                        messages.append(f"{field}: {', '.join(str(e) for e in errors)}")
                    else:
                        messages.append(f"{field}: {errors}")
                response.data = {"detail": "; ".join(messages)}
        elif isinstance(response.data, list):
            response.data = {"detail": "; ".join(str(e) for e in response.data)}
    return response
```

This matches what `api.js` on the frontend expects: `throw new Error(data.detail || ...)`.

## 17. Production Deployment (Render)

The `render.yaml` in the project root defines the service:

```yaml
services:
  - type: web
    name: learnpython-api
    runtime: python
    rootDir: backend
    buildCommand: pip install -r requirements.txt && python manage.py collectstatic --noinput
    startCommand: gunicorn learnpython.wsgi --bind 0.0.0.0:$PORT
    envVars:
      - key: SECRET_KEY
        generateValue: true
      - key: DEBUG
        value: "false"
      - key: PYTHON_VERSION
        value: "3.11"
      - key: CORS_ALLOWED_ORIGINS
        value: "https://your-frontend-domain.vercel.app"
```

### Post-deploy steps

1. Open the Render shell for your service.
2. Run: `python manage.py migrate`
3. Run: `python manage.py seed`

### Gunicorn workers

By default Gunicorn spawns `(2 * CPU_COUNT) + 1` workers. On Render's free tier (1 CPU), this is 3 workers. Each Django request that calls `run_code` blocks a worker for up to `SANDBOX_TIMEOUT_SECONDS`. If you expect concurrent code execution, increase workers or use async workers (`gunicorn -k uvicorn.workers.UvicornWorker`).

### SQLite on Render

Render's disks are ephemeral on free tier — the SQLite file is lost on each deploy. To persist data across deploys, either:
- Use a Render Persistent Disk (paid), or
- Switch to PostgreSQL (Render has free PostgreSQL add-ons)

For the curriculum data this doesn't matter much — just re-run `python manage.py migrate && python manage.py seed` after each deploy.
